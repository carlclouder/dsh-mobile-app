## 3. 正常使用所需的必要延拓

恢复前把可读仓库复制到 C 盘独立目录，包含 .git、工作区、私有配置、签名材料与未跟踪日志。排除可重新生成且体积较大的 .gradle、.toolchain、app/build 三个目录；它们不作为恢复来源。源文件与副本逐个校验 SHA-256。

未引用但仍可读取的 Git 文件对象和目录对象也随完整 .git 复制保全。审计已确认一个旧目录快照和一个仅有 Markdown 格式差异的文档对象，没有更新的遗失提交。恢复报告列出这些线索，保留它们而不替代 HEAD 正文。

最后同步远端跟踪引用缓存，消除 github/main 过期引起的“领先一个提交”假象。同步只读取远端，不向远端写入。

## 4. 架构层与职责

证据层读取文件字节、Git 对象、远端引用和损坏日志，提供可核对的输入。保全层把输入复制到 C 盘并验证，确保恢复失败时仍有原始证据。恢复层只替换明确受损的文件和索引。验收层独立比较前后内容，并执行真实 Git 命令。

这样划分是为了让恢复动作只能使用已经核实且已备份的内容。验收独立于“命令执行成功”，避免把文件写入成功当成内容恢复成功。

## 5. 功能模块关系

损坏识别模块向备份模块提供路径和字节特征。备份模块向恢复模块提供已验证的副本位置。对象读取模块向文档恢复模块提供原始字节。日志修复模块向引用记录模块提供完整有效前缀。索引重建模块从 HEAD 目录树读取文件条目。最终验收模块读取所有前后清单与 Git 命令结果。

模块使用完整路径、内容哈希和退出码交流，不通过控制台里被截断的正文传递文件。

## 6. 解耦设计

备份模块不解释源码或私有配置，只复制字节并校验。文档恢复模块不依赖应用的运行环境，只依赖经过 fsck 验证的 Git 对象。索引重建不写工作区。日志修复不改变分支指向。

这些边界避免恢复索引时覆盖用户文件，避免恢复日志时把旧提交当成当前版本，也避免保全私有文件时泄露内容。

## 7. 内聚与修改边界

原始复制、哈希清单和备份校验归入同一个保全步骤，因为它们共同决定恢复是否允许继续。文件对象读取、严格解码、原始字节写入和回读归入同一个内容恢复步骤，因为它们一起保证正文与编码正确。日志有效前缀判断与移除损坏尾部放在一起，防止保存半行记录。

本次工作脚本和日志放在 C 盘恢复目录的 work 与 outputs 子目录，项目方案放在 docs/requirements。恢复脚本只是本次操作记录，不增加应用模块或永久安装入口。

## 8. 具体执行流程与失败处理

1. 固定当前 HEAD 和需要恢复的路径，同时核对 HEAD 符号引用仍指向 refs/heads/main，并检查 index.lock 不存在。若切换分支、HEAD 改变、出现并发写入或损坏范围与方案不符，停止写入并重新检查。
2. 将仓库复制到 C 盘目录 `C:\Users\Carl\.codex\recovery\dsh-mobile-app\2026-10-13-64edfe91\snapshot`。复制不删除源文件。Robocopy 退出码小于 8 后，逐个比较源文件与副本的 SHA-256；任何缺失、读失败或哈希不同都停止。
3. 在 C 盘副本中重建索引，并运行 git fsck --full --no-progress。副本验证失败时只保留证据，不写原仓库。已完成的测试显示，同值 git update-ref HEAD 会追加 HEAD 日志，但直接分支及 origin/main 不追加日志。本版只要求新增一条 HEAD 恢复记录，main 与 origin/main 保留完整有效前缀。
4. 从 HEAD 提取两份文档对象和提交消息，直接读取标准输出字节。严格 UTF-8 解码验证，不允许零字节或额外字节顺序标记。先在 C 盘存储恢复字节和哈希。
5. 对三份损坏日志，只在首个零字节之前的内容以换行结束、每行字段合法、剩余字节全部为零时修复。出现中间损坏或半行时停止自动修复。
6. 每次写入前重新核对 HEAD 提交编号及 HEAD 符号引用，并核对待替换文件仍与备份相同。写入同目录临时文件，回读校验，再用文件替换方法替换目标。替换方法提供明确的同盘备份路径 `.git/recovery-originals/64edfe91/相对路径`，不传空备份参数；C 盘原始副本仍独立保留。若替换失败，保留临时文件及原始副本，报告实际错误，不绕过失败。
7. 用不存在的独立 GIT_INDEX_FILE 路径执行 git read-tree 和固定的已验证提交编号，得到新索引并核验条目，再以文件替换方法替换损坏索引。命令不带 -u，不更新工作区，不采用 reset --hard。
8. 对已清理的 HEAD 日志，使用一次同值 update-ref HEAD 追加“修复损坏日志后确认当前引用”的新记录。main 与 origin/main 日志只保留有效前缀，不调用同值更新，不手工追加记录。新记录明确属于本次恢复，不伪造原始被覆盖记录。验证四个引用和 HEAD 符号引用均未改变。
9. 对 GitHub 和 Gitee 执行有限的 main 拉取，以核实远端和更新跟踪缓存，不执行推送。网络失败不回滚已成功的内容恢复，但在报告中标出缓存尚未同步。
10. 比较其余 166 个文件、未跟踪日志、私有配置和签名文件的前后原始哈希。执行 status、diff、reflog 和 fsck，记录结果。保存恢复报告，更新本方案的实测结果。只暂存 `docs/requirements/2026-10-13-Git损坏恢复方案.md`；两份恢复文档应与 HEAD 一致，不能为了提交制造额外差异。核对暂存清单只有本方案，执行差异空白检查，将中文提交说明写入 C 盘 work 文件再通过 git commit -F 创建提交。

11. 推送前重新查询 GitHub 与 Gitee 的 main。若任何一端已出现未经本任务核实的新提交，停止推送并报告该端差异，不强推、不自动覆盖其他任务的提交。两端仍为恢复基线时，使用 origin 的两个已配置推送地址推送；随后不只看总退出码，而是分别查询两端 main，逐项比较是否等于新本地提交。仅一端成功时保留该端结果和本地提交，针对失败端正常重试并再次查询，不回退成功端。持续失败时明确标记失败端未同步。

第 2 版方案修改发生在初始保全之后。后续取得开工确认后，必须先在独立的执行目录再次保全当前工作区并建立新清单，初始 snapshot 保持原样；这样不会把合法的方案修订误当成并发损坏，也不会覆盖第一份证据。恢复脚本随后按本版修订并先在独立副本完整预演，预演通过才替换原仓库文件。

## 9. 判定算法与边界

非空全零文件判定为“长度大于零，且每个字节均为零”。空文件不自动判定损坏。二进制签名文件允许包含零字节，只检查全零状态并保全原始哈希。

文档恢复以 HEAD 中对应文件对象的字节为唯一正文来源。写回后先核对原始 SHA-256，再用 git hash-object --path 检查 Git 规范化后的哈希。这样既能证明字节一致，也能兼容现有自动换行转换配置。

日志前缀必须逐行满足两个 40 位十六进制对象编号、身份信息、时间戳、时区以及制表符后的操作说明。只允许移除连续零尾部，不删改有效历史行。没有完整前缀则停止该项。

备份清单按相对路径保存长度与 SHA-256；不把文件正文写进日志。文件量增加时逐文件计算，内存只保留清单和单文件缓冲。读不到任何必需文件均视为阻塞，不能用忽略错误后宣称全部保全。

## 10. 主要接口定义

本次使用的实际命令已核对本机帮助。Git 对象通过进程的标准输出二进制流读取，避免 shell 文本重定向改变中文编码或换行。

| 调用方与接口 | 输入 | 输出 | 失败表示与调用方动作 |
| --- | --- | --- | --- |
| 备份步骤调用 Robocopy | 源目录、独立副本目录、三个明确排除目录 | 副本、复制统计及日志 | 退出码大于等于 8 时停止；小于 8 仍须校验哈希 |
| 对象读取步骤调用 git cat-file blob | 固定 HEAD 与仓库相对路径 | 原始文件字节 | 非零退出码或解码失败时不写原文件 |
| 提交消息步骤读取 git cat-file commit | 固定 HEAD | 提交头之后的原始消息字节 | 找不到空行分隔或消息不合法时停止 |
| 索引步骤调用 git read-tree HEAD | 指向不存在路径的 GIT_INDEX_FILE | 新索引 | 非零退出码时保留原索引及备份 |
| 引用步骤调用 git update-ref | HEAD、固定当前值、相同期望旧值、恢复说明 | 引用不变、HEAD 日志新增一条记录 | 非零退出码、记录条数不符或引用变化时停止并保留证据 |
| 跟踪缓存步骤调用 git fetch | 现有远端名、main、禁用标签和子模块递归 | 更新远端跟踪引用及拉取记录 | 非零退出码时保留已恢复文件，记录该端缓存未同步，不推送 |
| 验收步骤调用 status、diff、fsck | 原仓库及恢复后文件 | 工作区状态、差异、对象完整性结果 | 出错时不得判定整体恢复完成 |
| 文档提交步骤调用 git add 与 git commit -F | 唯一本方案路径、C 盘中文说明文件 | 仅含本方案的新提交编号 | 暂存其他文件、差异检查失败或提交失败时不推送 |
| 推送步骤调用 git push origin main 与 git ls-remote | origin 的两条已配置地址、main、新本地提交 | 每端实际提交编号与退出码 | 任一端不一致就标为未同步；保留已成功端，不强推 |

脚本输入为固定的 RepositoryPath 与 RecoveryRoot。输出清单包含相对路径、原始长度、恢复来源、恢复后哈希、各验证退出码与不能恢复的事项。该清单使用无字节顺序标记 UTF-8，读取后必须能正常解析。
