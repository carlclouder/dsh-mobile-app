## 1. 需求确认与证据

用户报告：App 发送消息后卡住；WebUI 中消息均处于队列，同时出现交互选择框。
用户推测：App 没有显示交互，导致后续消息无法继续。
用户曾要求用最新包安装本地模拟器复现，随后明确改为直接分析源码，无需复现。
用户不记得原会话名称，因此不能认定原现场具体是审批还是提问。
用户随后明确：“本会话不在审批；尽快测试完成修复；测试按gif规则走”。
本次按这条新指令直接完成实现与测试，并恢复模拟器界面验收，不再停在方案或提交审批。

已确认的源码链路：

| 环节 | 证据 | 结论 |
| --- | --- | --- |
| 接收 | `EventStreamService.kt:255-259` 仅启动会话列表轮询及 `workspace/follow`；旧交互帧入口位于 `:597` | 当前活动通道没有向审批、提问状态机输入交互 |
| 数据与显示 | `DshRepository.kt:106-123`；`ConversationViewModel.kt:148-157`；`ConversationActivity.kt:740-784` | 页面已有卡片，但上游没有提供挂起交互 |
| 回答 | `DshApiClient.kt:298-310、594-623` | 审批和提问仍发往旧 `/api/respond`；只补显示仍不能闭环 |
| 新版宿主 | `@deepseek-ai/dsh-api-gateway/lib/index.js:773-833、883-955` | 通过 `/api/remote.mux` 上的 `$events` 接收交互，通过 `$events/result` 回答 |
| 排队 | `@deepseek-ai/dsh-api-session-controller/lib/index.js:882-883`；`@deepseek-ai/dsh-agent-loop/lib/index.js:800-807、854-857、1154` | 普通消息进入下一回合队列；当前工具等待回答时，当前回合尚未结束，后续消息继续排队 |

结论是交互通道存在确定缺口，且与队列消费逻辑组合能够解释用户现象。
原会话的具体触发事件未确认；不能把所有排队现象都归因于交互。

## 2. 范围

本次修复交互接收、审批与提问回答、跨端处理后的撤卡、断线恢复，以及默认超时提问的稍后回答。
沿用现有卡片，补齐问题详情、选项说明、回答中与连接异常的必要提示。
同时覆盖通知栏审批按钮，避免页面能回答而通知仍走旧接口。

保留消息发送的 `mode=queue`、消息历史合并、工作区订阅及认证行为。
不迁移全部会话流，不重构队列，不自动选择答案，不把普通消息当作交互回答。
当前阶段不升级宿主、不发布、不推送。模拟器用于修复后的界面与交互验收。

## 3. 必要延拓

新版 `ask_user_question` 默认等待 120 秒，默认走限时提问。
依据：`@deepseek-ai/dsh-tool-ask-user/lib/index.js:64、180-198`。
因此必须覆盖等待期间回答和超时后回答，不能只显示一个随后消失的问题。

还必须处理打开 App 前已有交互、断线期间出现交互、WebUI 先回答、重复点击及网络结果不确定。
问题的详细内容是选择依据，特别是方案审批；不能只显示批准按钮而省略待审内容。

## 4. 架构

保留“Compose 页面 → ViewModel → 仓库与状态机 → 网络客户端 → 宿主”的分层。
新增小型现代交互协议模块，负责现代帧、交互地址和提问等待状态。
订阅模块负责连接生命周期，不持有页面；页面不解析网络帧或直接请求接口。

沿用现有状态机发布卡片和通知，避免另建一套页面状态。
旧协议的解析和回答分支保留，由明确的交互来源区分新旧回答路径。

## 5. 模块关系

1. 前台服务启动现代交互订阅，与既有工作区订阅分别管理生命周期。
2. 订阅模块解析事件并交给状态机；状态机更新仓库中的审批、提问和连接状态。
3. 会话列表轮询继续提供宿主快照，并从可用投影恢复超时后仍可回答的问题。
4. ViewModel 读取卡片、保存按题草稿、发起回答并防止重复提交。
5. 网络客户端按交互地址调用现代或旧版接口；通知按钮使用同一回答方法。
6. 本机提交回执、宿主取消事件及权威投影共同收敛卡片；普通消息仍由宿主队列消费。

## 6. 解耦

现代帧不伪装成旧协议信封，显式保存 `clientId`、`eventId`、所属会话和可选 `callId`。
业务卡片读取统一交互信息，回答适配层根据来源编码请求。
这样页面无需理解不同网络信封，也不会把新接口错误地包成旧 `args.request`。

## 7. 内聚

协议模块集中处理解析、精确参数和关联标识。
订阅模块集中处理连接、等待声明、定时器、取消和重连。
状态机集中处理挂起项、去重、跨端撤销和通知决策。
ViewModel 集中处理本会话草稿、提交状态和提示，继续沿用现有卡片布局。

## 8. 主要流程

1. 启动时连接 `/api/remote.mux`，打开 `endpoint="$events"`、`payload={args:{}}` 的逻辑流。
2. 收到 `ready` 保存本代 `clientId`；收到 `waterfall` 读取顶层 `agentId`、`eventId` 和 `request`。
3. `approval/request` 映射为审批卡；本次内部审批标识使用 `eventId`，不要求新版载荷存在 `approvalId`。
4. `user-questions/request` 映射为提问卡；限时问题先打开 `userQuestions/attachWait`。
5. 等待声明首帧携带 `remainingMs`，以单调时钟计算本地截止时间；用户提交后等待宿主确认收敛。
6. 到期时发送标准超时拒绝，释放等待声明；不能无限持有声明，否则宿主计时被暂停。
7. 超时取消只撤销活动回答地址，问题是否继续显示由 `userQuestions` 和 `inbox` 投影决定。
8. 超时后的 `continued` 问题通过 `userQuestions/answer` 提交；已在收件箱排队的回答不得再提交。
9. 本机回答受理后发出带完整目标的本地提交事件，服务只撤销仍匹配该目标的活动卡、等待声明和通知。WebUI 先回答或宿主取消时，按取消事件或投影撤销。
10. 连接断开立即停用旧回答目标和等待声明；重连后接收宿主重放并按稳定键恢复，不重复提醒。
11. 未实现或无法呈现的交互返回 `next`，交由其他客户端处理；不认领后静默搁置。
12. 换服务器、服务销毁及协程取消时，关闭本任务的连接和定时器；旧世代回调不得覆盖新地址状态。

现代交互不得因历史 `origin=subagent` 被直接丢弃。
宿主允许历史子会话恢复为实时根会话后提问；是否允许发起交互由宿主判断。

## 9. 状态、算法与边界

- 普通交互按 `eventId` 去重；带 `callId` 的提问以“会话 + callId”保存卡片与草稿，避免超时切换丢答案。
- 回答地址和连接世代一起更新；旧 `cancel` 不能删除已经换代的新目标。
- 重连时保留题目草稿，停用旧地址；使用新 `clientId` 的待答重放更新提交目标。
- `attachWait` 首帧前结束或报错时，释放声明并重新对账，不保留可提交的失效活动目标。
- 默认不暂停本地限时计时；按宿主给出的剩余时间到期，保留稍后回答能力。
- 优先使用既有 `session/list` 的 `projections.values`。缺失时仅为当前会话补读 `session/projections`；缺失或读取失败不当成空快照。
- `userQuestions.active` 决定仍可回答的问题；`inbox.next-step/next-turn` 中 `source.kind="user-question-reply"`、相同 `callId` 的项说明回答已排队，应禁用再次提交。
- 回答网络失败保留选择和补充文字，显示可重试提示；不自动重发，也不自动发送后续队列消息。
- 网关对已消失事件可能仍返回成功，因此 HTTP 成功只表示请求提交，最终状态以取消事件和投影为准。
- 宿主提交入口先移除提交客户端的投递，再向其他客户端广播取消；提交者不保证收到 `cancel`。因此本机受理必须主动按完整目标收敛，不能永久等待自己的取消帧。该修正不影响其他客户端先作答时的取消处理，也不得撤销换代后的新目标。
- 每次状态合并按交互数量线性遍历；输入为空时正确保留其他来源状态，畸形数据进入可观测错误分支。

## 10. 接口

| 接口 | 精确输入 | 结果与处理 |
| --- | --- | --- |
| `$events` 流 | `payload={args:{}}` | `ready`、`waterfall`、`cancel`；流终止时重连 |
| `$events/result` | `payload.args={clientId,eventId,outcome}` | 正常业务响应无值；失败保留草稿并提示 |
| 审批回答 | `outcome={kind:"result",value:"allowed-once"}` 或 `"rejected"` | `value` 为裸字符串，不能沿用旧审批对象 |
| 提问回答 | `outcome={kind:"result",value:{answers:[{id,selected,custom?}]}}` | 不再包旧版的 `sessionId/answer` 外层 |
| 未支持交互 | `outcome={kind:"next"}` | 委派，不替用户作决定 |
| 提问超时 | `outcome={kind:"rejected",error:{name:"UserQuestionError",code:"ASK_TIMED_OUT",message:"回答等待时间已结束"}}` | 名称、代码和字符串消息必须完整，否则宿主不能转为稍后回答 |
| `userQuestions/attachWait` 流 | `payload.args={agentId,callId}` | 首帧 `remainingMs`；释放流即释放等待声明 |
| `userQuestions/answer` | `payload.args={agentId,callId,answer:{answers:[...]}}` | `true`：回答已排队；`false`：刷新确认当前状态；`REPLY_QUEUED`：查投影并禁止重复；网络失败保留草稿 |
| `session/projections` | `payload.args={request:{sessionId}}` | `asOfSeq/values`，会话不存在可返回 `null`；读取失败不清空卡片 |

网络层新增明确接收原始命名参数、支持布尔及空值的交互入口，复用现有认证和信封解析。
既有 `call()` 默认添加 `args.request`、且仅接受对象结果，不能直接用于上述所有新接口。
旧 `/api/respond` 的回执处理保留。新通知携带完整回答地址，失效地址提示重新打开 App 连接。

## 12. 实际使用场景

1. 用户只开 App；宿主要求选择。App 显示完整问题，回答后当前工具继续，宿主正常消费后续消息。
2. 用户先在 WebUI 发起任务，后开 App。宿主重放未处理交互，App 可继续回答同一问题。
3. 用户断网重连。题目草稿保留；连接恢复前提交受限，恢复后使用新回答地址。
4. 用户在 WebUI 先完成选择。App 随取消或投影撤销卡片，不再发出重复答案。
5. 提问超过默认等待时间。活动回答地址结束，但稍后回答卡片仍可恢复；提交一次后显示待处理状态。
6. 用户在等待选择时继续发普通消息。消息保持队列语义，App 说明当前等待交互，不擅自把这些消息变成答案。
