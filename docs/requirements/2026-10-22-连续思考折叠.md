# 连续思考步骤默认折叠

日期：2026-10-22。状态：已实现（0.1.207），222 项测试与双包构建通过，核心设备场景已验证。基线：41ad5f9。分支：codex/live-thinking-preview。
用户已确认采用"无正文、无可见工具结果的连续步骤合并成一行收起"的方案。

## 1. 需求确认

用户原话：聚焦 dsh-mobile-app 项目；对于中间连续的思考过程输出框，且没有具体输出的，需要增加默认折叠功能，避免无有效信息的思考结果框占大量页面；但是，输出带有明确输出的，例如第一行和最后一行，则不能归并折叠。

用户提供的真机截图：每步助手消息一个气泡，气泡首行是收起态「💭 思考过程 · 点按展开」。
中间 6 个气泡只有工具调用行（pwsh、grep、subagent）与时间，没有正文；首尾两个气泡带说明文字。

我的推断（用户已确认方案，但两句措辞属推断）：
1.「没有具体输出」指该步既没有助手正文，也没有工具结果正文，只剩思考标签与工具调用一行摘要。
2. 只有一步时不折叠，因为它不构成「连续」。

不做：带正文步骤（截图第一行与最后一行）不归组、不折叠，保持现有气泡外观。

## 2. 范围

本次只改会话列表渲染层，新增纯 Kotlin 分组器。
不修改消息解析、历史合并、发送、排队、审批、提问、通知和顺序对齐逻辑；上一轮刚完成顺序修复，此路径风险最高，本轮不动。
不做 WebUI 那种按工具类型（读取/搜索/写入）分类统计的摘要标题，避免引入工具名到类别的映射表。

## 3. 必要延拓

分组后列表项数变少，「跳到底部」「贴底跟随」「判断是否接近底部」使用的项数必须改为渲染项数，否则跳底少滚或滚过头。
展开状态按组键（组内首步消息键）记忆，流式每 80 毫秒刷新列表时不能重置，也不能因组增长（后续步骤并入）而丢失。
组内各步沿用现有渲染部件：思考行仍可单独展开，工具调用行仍可单独展开，时间行保留。

## 4. 架构

新增 `ui/ThinkingProcessGrouping.kt`：纯 Kotlin 分组器，输入消息列表，输出渲染项列表，可单测，不依赖 Compose 与 Android。
`ui/ConversationActivity.kt`：列表改为渲染分组器输出；新增组气泡组件；把助手消息内容渲染抽成一个可复用组件，供独立气泡和组内各步共用。
`ui/ConversationViewModel.kt` 不改：消息仍是原来的 `UiMessage` 列表，分组只在渲染时发生。

## 5. 模块关系

页面从 `viewModel.messages` 取列表 → 分组器生成 `List<ConversationItem>` → 列表逐项渲染：`Message` 交给原有 `MessageBubble`，`ProcessGroup` 交给新组气泡。
组内展开时按原顺序调用抽出的助手内容组件，时间行仍由各步自己输出。

## 6. 解耦

分组器只认识 `UiMessage` 的 role、text、toolCalls、toolResults、key 五个字段，不知道 Compose、状态流或网络。
页面不判断"什么算无输出"，只按分组器给的项渲染；将来调整折叠口径只改分组器与测试。

## 7. 内聚

"是否可折叠""连续几步""摘要里的步数与工具调用数"全部归分组器；
"展开/收起状态""点击行为""气泡外观"归页面；
消息产生与合并仍归 ViewModel，互不越界。

## 8. 流程

1. 消息列表每次变化，分组器从头扫描一遍。
2. 遇到可折叠步骤（助手 + 非流式占位 + 正文空白 + 无工具结果）就累加进当前批次；否则先结算当前批次，再输出这一条不可折叠项。
3. 结算规则：批次长度 ≥2 输出一个思考组，长度 1 原样输出为单项，长度 0 什么也不输出。
4. 页面渲染：收起态只显示一行摘要；展开态**还原成原来一个个独立气泡**逐步渲染（不是把多步塞进同一个框）。
5. 点击摘要行切换该组展开状态；状态以组键存于页面状态，列表重建不丢。只有手动点开才恢复，列表刷新不会自动展开。
6. 列表项数 = 渲染项数 + 底部实时思考预览占位（若显示），跳底与贴底都按这个数计算。

## 9. 算法与边界

可折叠判定：`role == ASSISTANT && key != "__streaming__" && text.isBlank() && 没有任何非空工具结果正文`。
"有没有输出"按界面实际能看到的判定，不按数据结构里有没有条目判定：宿主会给大多数工具步骤挂 `tool/result` 条目，但当前版本这些条目的正文是空串（本项目会话历史实测：188 个无正文步骤中 187 个挂着结果条目，正文长度全为 0），界面按现有规则整条跳过空正文结果，用户看不到任何输出，这类步骤仍属"没有具体输出"。
空白正文包含空格、换行、制表符，`isBlank()` 已覆盖。
流式占位消息永不入组：它的正文与思考还在增长，且底部已有实时单行预览。
带可见工具结果的步骤不入组：结果正文属于"具体输出"，按用户要求不折叠。
用户消息、上下文注入、错误提示、独立工具结果、其他角色消息都会打断连续批次。
末尾未结算的批次照常结算，不做特殊处理。
组键取组内首步消息键；首步被历史对账替换后组自然重组，展开状态按新键失效，不会串到别的组。
摘要数字：步数 = 组内消息数，工具调用数 = 各步 toolCalls 数量之和。
收起态行首带 `▸` 折叠标识，尾部提示「点按展开」/「点按收起」。
列表尾部的组（`isTail`：它是最后一组，且其后没有带正文的助手回答）收起时，改为「▸ 💭 N 步」+ 只滚动显示该组最新一条思考内容（钉尾横向滚动，无扫光）；其后一旦出现带正文的回答就退回普通摘要行。

## 10. 接口与源码依据

```kotlin
internal sealed interface ConversationItem {
    data class Message(val message: UiMessage) : ConversationItem
    data class ProcessGroup(
        val key: String,
        val steps: List<UiMessage>,
        val toolCallCount: Int,
        val isTail: Boolean = false,
    ) : ConversationItem
}

internal object ThinkingProcessGrouper {
    const val MIN_STEPS = 2
    fun group(messages: List<UiMessage>, streamingKey: String): List<ConversationItem>
}

internal fun processGroupLabel(stepCount: Int, toolCallCount: Int, expanded: Boolean): String
internal fun processGroupTailLabel(stepCount: Int): String
```

源码依据（现行实现）：
`ConversationActivity.kt` 的 `ConversationScreen` 用 `items(messages)` 逐条渲染、`listItemCount = messages.size + 1`；`MessageBubble` 的助手分支依次渲染 `CollapsibleThinking`、正文、`ToolCallCard`、`CollapsibleToolResult`、`TimestampLine`；`CollapsibleThinking` 收起态文案为「💭 思考过程 · 点按展开」；流式占位键在 `ConversationViewModel.STREAMING_KEY`。
`ConversationViewModel.appendToolResult` 把工具结果并入"最后一条带工具调用的助手消息"，所以组内靠后步骤可能带结果并因此不被折叠，这与"有具体输出不折叠"一致。

WebUI 参照（只作口径对齐，不复制实现）：`dsh-client-ui-chat` 的 process 分组把一轮中连续的处理步骤收成一组，标题用「已思考」「N 次工具调用」这类文案拼接，组内步骤不逐条常显。

## 12. 实际场景

打开一个跑了多次工具调用的会话：过去要占几屏的连续思考气泡，变成一行「💭 思考过程 · N 步 · M 次工具调用 · 点按展开」，真正的回答仍以完整气泡显示在下方。
用户在中间步骤里找某一行的 pwsh 参数：点开这一行摘要，组内各步按原顺序展开，原样可读，再点收起。
回合进行中：新的无正文步骤持续并入组，行内数字增长；底部实时思考预览保持不变。
带正文的步骤（例如"我先核对本机实际支持情况，再回答。"）始终是独立气泡，不并入组。

## 实施与验收结果

实现：新增 `ui/ThinkingProcessGrouping.kt`（纯 Kotlin 分组器 + 摘要文案），`ConversationActivity.kt` 的列表改为渲染分组结果，助手内容抽成 `AssistantMessageContent` 由独立气泡与组内各步共用，新增 `ProcessGroupBubble`；展开状态按组键提升到页面，`listItemCount` 与自动贴底的触发键都改按渲染项数计算。`ConversationViewModel` 未改动，消息产生与合并逻辑不受影响。`ThinkingStreamRow` 增加 `label` 与 `sweep` 参数，供尾部折叠行复用同一条钉尾滚动行。

用户两次纠正后的最终口径（已实现并验收）：
1. **折叠是折叠，不是合并**：点开后必须还原成原来一个个独立气泡（各自边框、时间行、自己的「思考过程 · 点按展开」），不能把多步塞进同一个框；单个气泡的点按展开能力与原实现完全一致。
2. **折叠是追加不是替换**：两条正文之间的多条照样折叠；列表尾部那一组收起时改成「▸ 💭 N 步」+ 只滚动显示最新一条内容，其后一旦出现带正文的回答就退回普通摘要行。
3. **折叠标识明确**：所有折叠行行首带 `▸`，并写明步数、工具调用数与「点按展开 / 点按收起」；只有手动点开才恢复，列表刷新不会自动展开。

编码完成后统一跑全量测试与设备验收：
- `testDebugUnitTest` 全量 222 项通过（失败、错误、跳过均为 0），其中新增 30 项分组、尾部标记与文案用例。
- `assembleDebug`、`assembleRelease` 成功，版本 0.1.207（208）；正式签名校验通过。
- 模拟器（Android 15，1080×2400）安装 Debug 包，经 `adb reverse` 连接本机真实 dsh：打开用户截图同一会话（13:38 问子代理并发），中间 7 个空壳步骤默认折叠成一行、带正文步骤仍独立、点开还原为 7 个独立气泡、再点收起；另一条真实会话「dsh」末尾 2 个无正文步骤验证尾部折叠行（`▸ 💭 2 步` + 最新内容滚动），点开同样还原独立气泡；跳到底部按项数正常出现与消失。

已知限制（本轮不处理，避免牵动消息模型）：

1. 分组只按"连续步骤"切分，不按回合切分。宿主若存在不经用户消息就开新回合的续跑，上一回合末尾与下一回合开头的空壳步骤会被并成一组，摘要里的步数跨回合。要修需要把 turn 边界喂给分组器，属 ViewModel 改动，另开任务。
2. 空正文的独立工具结果消息在界面上不可见，但按方案仍会打断连续批次；诊断时看到"两组之间夹着看不见的东西"属预期。
3. 步数或工具调用数到三位数时，摘要可能把「点按展开」挤成省略号；整行仍可点，只影响可发现性，需真机窄屏确认。
