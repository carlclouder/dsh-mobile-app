# 归档过滤验证（2026-10-10 补充）

## 用户报障（原话）
"全部中人有大量 历史已归档会话 污染页面"

## 验证方法（决定性）
1. Node 探针直连宿主，取权威数据：会话总数 **460**、归档集合 **157**、按归档过滤后应显示 **303**；
   并取出 8 个"应被隐藏的归档会话标题"样本。
2. 模拟器 App（debug，代码同 release v0.1.183）在会话列表页 dump UI，逐一比对标题。

## 验证结果
| 检查项 | 结果 |
|---|---|
| 归档会话标题（内核拦截系统 / 修复插件点击条目列表滚顶问题 / 同源图片渲染测试 / 审核需要 代码论据佐证 不可 / Mode probe reply OK / 图片显示验证） | **全部未出现** ✓ |
| 活跃会话（dsh-app-modile / AI经验卡与需求确认规则 / 部署codex） | 正常出现 ✓ |
| 工作区筛选条与分组 | 正常 ✓ |

证据文件：`archive_filter_verified.png`（界面截图）、`ui_dump_archive_filter.xml`（UI 树原始 dump，可逐条核对）。

## 结论与未覆盖场景
- **App 侧归档过滤逻辑本身正确**：状态机 `sessionSnapshot()` 执行 `removeAll(archivedSessionIds)`，
  数据来自 `/api/remote.mux` 的 `workspace/follow` baseline 帧（本目录 README 已记录协议细节）。
- **未覆盖**：真机（用户手机）未实测。若用户手机上仍显示归档会话，**首要怀疑是 App 版本旧**
  （旧版没有工作区流，拿不到归档集合，157 个归档会话会全部显示）。
- 另一可能：用户看到的其实是 **303 个未归档会话**（真实历史数据）。这属于"显示范围"策略问题，
  需用户定规则（如只显示最近 N 天、或折叠 30 天前的），不属于缺陷。
